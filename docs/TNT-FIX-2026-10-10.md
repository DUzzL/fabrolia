# TNT mechanics fix — Minecraft 26.3, 2026-10-10

The earlier review is archived in `TNT-CODE-REVIEW-2026-10-10.md`. This change
addresses the confirmed scheduler and block-event deviations. It does not change
Vanilla TNT fuse length, explosion power, resistance, impulse or drag formulas.
The original player's specific world eater/replay is not available here.

## Runtime changes

- Regions remain ownership indexes. Each island first joins its regional queues,
  then visits a finite snapshot of the actual linked `EntityTickList` in Vanilla
  insertion order. Independent islands remain parallel. The global remainder
  uses the actual Vanilla consumer on Main after its own queue-only join.
- `IslandEntityPhaseScope` requires the live exact unit claim and a successful
  current queue-only dispatch receipt. Under that exclusive pass, complete block
  callbacks execute inline across owned region borders and the halo. Removing a
  TNT block therefore finishes before `wasExploded` creates its primed entity;
  another explosion cannot prime the same still-visible block again.
- Snapshot membership supplies the entity-phase birth cut, including births in
  a target region that has not yet been visited. Scheduled/block-event births
  before the cut retain their same-unit first tick. Existing vehicle, passenger,
  chunk-range, tick-token and compatibility gates remain in the per-entity path.
- A final TNT tick whose movement, portal processing or conservative blast
  footprint cannot be certified inside its island uses the existing all-island
  Main fence. The footprint reads the actual 26.3 explosion power (serialized
  range 0..128). Normal power-4 TNT within the halo retains its worker path.
- Block events have one canonical pending-identity set across shared, stashed,
  captured and active island queues. Dequeue removes one identity immediately
  before its callback, so reposting still-pending B from A is deduplicated.
  `clearBlockEvents` cancels every unconsumed queue suffix. Topology transfers
  preserve an admission's object identity and cannot resurrect a cancelled post.
  Callback bodies run outside the queue locks; lock order is level then island.
- Removed the detached block-event wave/local queue path. Retained the existing
  public region-dispatch API and reflected Rustmi integration names.

## Runtime mechanics comparison

Fresh reference `tnt-van-v2`: Minecraft 26.3 with only Fabric API, Carpet and
spark, no other gameplay mods or production datapacks. Eight cases, 40 checks:
PASS. Fresh candidate `tnt-fix-v3`: production-like mod set, eight cases,
53 checks including direct reference comparisons: PASS. Both shut down normally
without crash reports.

Cases run in `/tick step` and `/tick sprint`:

1. Older TNT at x=128.5 explodes before younger TNT at x=127.5 moves, despite
   their different region colors. One-tick position x=126.62687051993578,
   velocity x=-0.8556669071165599 and fuse=79 match the reference exactly.
2. Explosion-created TNT at x=128.5 waits for the next entity phase. Its first
   movement/gravity and next fuse decrement match Vanilla; the random shortened
   fuse retains Vanilla's range.
3. Two explosions encountering one TNT block create exactly one primed TNT and
   remove the block immediately.
4. TNT crossing x=128 retains one fuse and movement step per physical tick.
   Eight-tick x=133.46947949104973 and fuse=72 match the reference exactly.

The step fixture explicitly coherence-pins its island to Main's cadence for
reproducible unit counts; worker ownership and the island coordinator remain
active. An unpinned preliminary run showed multiple local units during a wall
step, so that run is not used as a one-step mechanics oracle. Vanilla's frozen
sprint startup admits one thaw tick before the requested sprint ticks. The
harness waits for sprint completion and asserts this physical fuse clock.
Normal unpinned behavior is tested by the general stand and performance runs.

The unchanged old jar (`tnt-old-v1`) fails the first blast-before-motion

although it receives the impulse. Its fuse still decrements once. The fixed

End-portal stand `tnt-end-v1`: 37 checks PASS using actual portal transfers,
unequal clocks, no End forceloads, saves, two restarts, scheduler off/on,
normal recovered sand placement and the next platform regeneration's sand drop.
All three server sessions shut down normally, with no crash reports.

Matched 120-second `items` + `pistons` scenarios completed as `tnt-perf-old-v1`

## Scope of the result

The reported damage is consistent with these scheduler deviations, but no
specific ten-failures-in-nine-hours replay has been reproduced. This validates
the identified mechanics and integration paths, not every possible mod setting
or world-eater build. The review's conditional Rustmi/Lithium/Carpet explosion
optimization concerns are separate and have not been changed in this patch.

## Follow-up: cost of the entity cuts (2026-10-10, evening)

Matched `items` + `pistons` profiles, baseline = the TNT-fix jar above
(`8a3bf474…`, run `claude-perf-base-v1`), candidate `a500514f…`
(`claude-perf-new-v2`); inclusive ms per Main tick:

| Frame | Baseline | Candidate |
| --- | ---: | ---: |
| Main `tickGlobalEntitiesInVanillaOrder` | 1.917 | 0.018 |
| Main whole-list snapshot copy | 0.628 | 0 |
| Island cut (snapshot + filter), workers summed | 1.326 | 0.992 |
| Region lookups inside the island cut | 0.312 | 0.039 |

With async islands every populated cell joins an island at the level-head
rebuild, so the global lane normally indexes no entity; Main now skips its
snapshot then and takes the exact path otherwise. Both cuts resolve each grid
key once. The global pass again re-routes a moved entity's region index.
Whole-run TPS on this 8 GB host is not comparable between runs (the same
baseline jar measured 3.9/9.7 and 2.9/7.2 local TPS in two runs; later runs
ran while the host swapped ~8–10 GB), so only the changed frames are claimed.

An island cut still copies and scans the whole level's list (about 18 ns per
level entity in a microbenchmark). An exact alternative was implemented and
validated (EntityTickList insertion stamps under the list monitor; each island
gathers its own regions' entities and sorts by stamp; randomized parity tests
against the real 26.3 list; TNT parity 53/53 async and 52/52 sync; raid runs
passed) but not adopted: the region-set walk plus sort costs about 100 ns per
own entity, 0.55 vs 0.20 ms per unit for two islands of 5,500 entities and
0.06 vs 0.22 ms for ten islands of 1,100. Large farm islands, where MSPT
matters most, would pay more. Reconsider it only if production shows many
small islands per dimension (`/fabrolia regions top verbose 100`).

Validation of `a500514f…`: 1,442 tests (1,434 passed, 8 optional skipped); TNT parity
53/53 async (`claude-tnt-v4`) and 52/52 sync (`claude-tnt-sync-v2`) against
`tnt-van-v2`; general stand 11/11 (`claude-vfy-v4`); original compact raid
farm with all eight waves and victory (`claude-raid-compact-v1`), loaded-ring,
low-distance and village-removal raid checks (`claude-raid-*-v3`).

`tnt-parity-driver.py` now starts the step cases only once the pinned island
is level with game time (`L == gt` while frozen). On a loaded host a pinned
island two ticks behind made up those ticks during the first multi-tick step,
so the pulse clock read 19990 instead of 19992; the unchanged baseline jar
failed the same way under the same conditions (`claude-tnt-base-v1`).
